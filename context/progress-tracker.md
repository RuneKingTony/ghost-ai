## Architecture Decisions

- `POST /api/liveblocks-auth` calls `getOrCreateRoom(roomId, { defaultAccesses: ["room:write"] })` rather than scoping access per-user via `usersAccesses`. Liveblocks' own docs (`create-rooms-manually` reference) note ID-token auth normally pairs with fine-grained `usersAccesses`/`groupsAccesses`, but that only applies at room-creation time — `getOrCreateRoom` ignores those params on rooms that already exist, so a second collaborator added after the room's first visit would never be granted access that way without also calling `updateRoom` on every auth request. Instead, this route's own `hasProjectAccess()` check is the actual gate (matching `architecture-context.md`'s "Liveblocks room tokens are issued only after verifying project membership" — the token is the checkpoint, not the room's own access list), and there is no public-API-key path in this app (only the private `authEndpoint` flow), so a room-level `room:write` default is safe: nobody reaches `getOrCreateRoom` without already having passed the project-access check.
- `proxy.ts` no longer calls `auth.protect()` for any `/api/(.*)` request — it returns early for those before reaching the `isPublicRoute`/`auth.protect()` branch. This was required by `06-project-api.md`'s "unauthenticated requests return `401`" rule: Clerk's `auth.protect()` (read from `@clerk/nextjs/dist/esm/server/protect.js`) redirects only for page requests and otherwise calls `notFound()`, i.e. a plain `404`, for anything without `Sec-Fetch-Dest: document`/`text/html` `Accept` — which is every `fetch`/`curl` call to an API route. Each handler in `app/api/projects/**` now does its own `const { userId } = await auth(); if (!userId) return 401` instead, matching Clerk's own resource-based-check guidance (see the still-open half of this in Open Questions). Verified with `curl` against a running dev server: all four endpoints (`GET`/`POST /api/projects`, `PATCH`/`DELETE /api/projects/{id}`) return `401` unauthenticated, where they previously would have 404'd at the middleware layer before this change.

- `app/globals.css` now defines the raw design tokens from `ui-context.md` (`--bg-base`, `--text-primary`, `--accent-primary`, etc.) as the source of truth in `:root`, and maps shadcn's semantic tokens (`--background`, `--primary`, `--border`, `--ring`, `--sidebar*`, ...) onto them so the untouched `components/ui/*` files render the dark theme automatically. `--primary`/`--ring` use `--accent-primary` (cyan); `--secondary`/`--muted`/`--accent` use `--bg-subtle`; `--destructive` uses `--state-error`.
- App-level Tailwind utility names (`bg-base`, `bg-surface`, `bg-elevated`, `bg-subtle`, `border-surface-border`, `border-subtle-border`, `text-copy-primary/secondary/muted/faint`, `text-brand`/`bg-brand`, `bg-accent-dim`, `bg-ai`/`text-ai`, `text-ai-text`, `text-error`/`bg-error`, `text-success`/`bg-success`, `text-warning`/`bg-warning`) are exposed via `@theme inline` in `app/globals.css`. Only `bg-base`, `bg-surface`, `text-copy-primary`, `text-copy-muted`, `border-surface-border`, and `text-brand` were named explicitly in `ui-context.md`; the rest were inferred to follow the same naming convention — flagging here in case a different name is intended.
- This app is dark-only (per `ui-context.md`), so `app/layout.tsx` applies the `dark` class to `<html>` unconditionally instead of building a light/dark toggle.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in` and `NEXT_PUBLIC_CLERK_SIGN_UP_URL=/sign-up` were added to `.env.local`. `03-auth.md` says to "use existing Clerk env vars, do not invent new ones" — these are Clerk's own standard SDK-recognized env var names (confirmed by reading `@clerk/nextjs`'s source), just not yet present in this project's `.env.local`; they were not renamed or replaced with anything custom.
- `lib/clerk-appearance.ts` holds the single `Appearance` config (theme + `variables`) passed to `ClerkProvider`, so every Clerk component (sign-in/up forms, the navbar `UserButton`) inherits the same token mapping from one place rather than each usage repeating `appearance` props.
